# Fraction Zone Economy MVP

Статус: черновик для обсуждения реализации.
Область: детерминированные потоки ресурсов внутри систем, принадлежащих фракциям.

## 1. Зачем это нужно

Текущее поведение - это только рыночный арбитраж:
- ордера станций создаются случайно на старте;
- нет runtime-цикла добычи/производства;
- ордера только уменьшаются после сделок;
- депозиты планет/лун есть, но экономикой не потребляются.

Итог: станции торгуют "чем попало", устойчивая производственная цепочка не формируется.

## 2. Цель MVP

Собрать минимальный замкнутый контур:
- периферия добывает сырье;
- ядро перерабатывает сырье в промтовары;
- домашняя система потребляет товары и создает стабильный спрос;
- трейдеры возят товары по реальным дефицитам/избыткам, а не по случайной стартовой инициализации.

## 3. Жесткие ограничения текущего кода

1. Источник уровня системы - существующий `StarSys.SecurityLevel`.
2. Базовую модель торговли сохраняем (`ExchangeService`, ордера, `Cargo`).
3. Для первого играбельного MVP не требуем миграции схемы БД.
4. Используем только уже существующие `items` из `Assets/Data/game.db`.

## 4. Модель уровня системы (из SecurityLevel)

Уровень определяется каждый глобальный ход:
- `Home`: `securityLevel >= 0.99`
- `Core`: `securityLevel >= 0.5 && securityLevel < 0.99`
- `Periphery`: `securityLevel > 0 && securityLevel < 0.5`
- `Neutral`: `securityLevel <= 0` (вне фракционной экономики)

Это убирает неоднозначность "кто основная фракция" и соответствует текущей модели данных.

## 7. Экономическая роль станций по уровню системы

Роль назначается станциям каждый глобальный ход.

- Периферия: `ExtractorTradePost`
  - производит L0 из локальных депозитов;
  - держит небольшой резерв;
  - продает основную часть L0.

- Ядро: `RefineryHub`
  - покупает L0, перерабатывает в `501..504`;
  - продает `501..504`;
  - держит средний резерв L0 и промтоваров.

- Домашняя: `CapitalConsumer`
  - покупает `501..504` и товары-поглотители `505..509`;
  - каждый ход потребляет `501..504`, чтобы поддерживать давление спроса;
  - сильная sell-сторона в MVP не обязательна.

## 8. Экономический цикл на ход (global step)

Выполняется один раз в глобальный день для неактивных систем (и опционально активной).

1. `Extract`:
   - для каждой периферийной системы считается генерация L0 по депозитам;
   - объем добавляется в `Cargo` станции.

2. `Refine`:
   - для каждой станции ядра крафтятся `501..504` из доступного L0;
   - применяется ограничение throughput на ход.

3. `Consume`:
   - для домашней станции снимается корзина спроса;
   - при нехватке остаточный спрос выражается в `buy` ордерах.

4. `RebuildOrders`:
   - для отслеживаемых товаров ордера собираются из целевого диапазона склада;
   - если `stock < targetMin` - создается/обновляется `buy`;
   - если `stock > targetMax` - создается/обновляется `sell`;
   - для одного товара убирается устаревший противоположный ордер.

5. `Clamp`:
   - ограничение объема ордеров по виртуальным лимитам и реальному складу;
   - ограничение ценового отклонения через `EconomyConstants.MaxPriceDelta`.

## 9. Политика ордеров (детерминированная)

Для каждой роли станции и каждого товара задаются:
- `targetMin`, `targetMax`, `desiredMid`.

Ценообразование через дефицит:
- `deficitRatio = (desiredMid - stock) / max(1, desiredMid)`
- `price = basePrice * (1 + clamp(deficitRatio, -D, D) * MaxPriceDelta)`

Значение `D` для MVP: `1.0`.

Это сохраняет текущий стиль цен, но убирает случайность.

## 10. Политика throughput (простая и стабильная)

### 10.1 Добыча

Для каждого депозита:
- `baseOutput = 20 units/day`
- `output = baseOutput * deposit.Availability * deposit.ResourcePurity`

Множитель по уровню системы:
- Periphery: `1.00`
- Core: `0.40`
- Home: `0.15`

Это дает заметный поток, но не превращает home/core в основные добывающие центры.

### 10.2 Переработка

Для каждого рецепта на станциях ядра:
- `maxBatchesPerDay = 10` (настройка);
- выполнять, пока есть входы и не достигнут лимит.

## 11. Точки интеграции в текущем коде

### 11.1 Сохранить, но переиспользовать bootstrap

`StationTradeBootstrap` должен перестать делать случайный full-market seed для фракционных станций.
Его роль в MVP:
- гарантировать наличие обязательных модулей;
- (опционально) задать минимальный стартовый запас.

### 11.2 Добавить экономическую стадию/сервис

Предпочтительно: новая глобальная стадия, например `GlobalEconomyStage`.

Порядок пайплайна:
- Input
- Economy
- AI
- Movement
- Interaction
- Combat
- Events

Причина: AI должен планировать маршруты уже по обновленным ордерам текущего дня.

### 11.3 Паритет активной системы

Чтобы избежать расхождения:
- либо тот же экономический апдейт применяется к активной системе в global stage;
- либо делается зеркальный local-апдейт.

Предпочтительно для MVP: один глобальный апдейт для всех систем раз в день.

## 12. Добавления в сценарии/конфиги

Максимально опираемся на уже существующие поля:
- `systems[].securityLevel` уже есть;
- `systems[].role` можно использовать как hint (необязательно);
- `systems[].stations[].type` должен начать маппиться на экономический шаблон, а не всегда в один дефолт.

Минимальный маппинг типа станции:
- `Default` -> по уровню системы;
- опционально явные:
  - `Extractor`
  - `Refinery`
  - `Hub`

## 13. Метрики валидации экономики

Снимать каждые 50 ходов:
- суммарная добыча по L0;
- суммарное производство по рецептам `501..504`;
- суммарный торговый объем по товарам;
- доля idle-трейдеров (`%` без задач);
- `stockout ratio` по корзине спроса домашней системы.

Критерии прохождения MVP:
- ненулевая добыча и производство как минимум у 3 фракций;
- ненулевая межсистемная торговля L0 и `501..504`;
- `stockout ratio` home ниже 70% после прогрева (первые 30 ходов);
- к 100 ходу нет коллапса ордеров в ноль.

## 14. Известные риски и контроль

Риск: домашний спрос слишком быстро опустошает рынок.
- Контроль: ограничить home consumption и поднять throughput ядра.

Риск: периферия перепроизводит и обрушает цены.
- Контроль: жесткий `max stock` на товар и снижение множителя добычи.

Риск: трейдеры зацикливаются на низкомаржинальных маршрутах.
- Контроль: требовать положительный net score и сохранить текущие проверки прибыльности.

## 15. Фазы внедрения

Фаза 1 (играбельно):
- добавить группы товаров, рецепты v0, профили ролей станций;
- добавить глобальный экономический тик (`extract/refine/consume/rebuild orders`);
- отключить случайный market seed для фракционных станций.

Фаза 2 (стабилизация):
- добавить логирование метрик и балансные константы;
- добавить опциональное производство `505/506`;
- при необходимости расширить route score штрафом за безопасность.

Фаза 3 (контент):
- расширить список товаров в БД под полное покрытие `Recipes.md`;
- вынести рецепты из документа/статической таблицы в data-driven конфиг.

## 16. Вне области MVP

- полный L2-L5 проддерево из `Recipes.md`;
- динамические налоги, пиратское давление, эмбарго, дипломатические эффекты;
- полноценная бюджетная модель NPC с финансовыми ограничениями.
