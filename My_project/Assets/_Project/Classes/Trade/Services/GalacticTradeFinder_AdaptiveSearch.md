# GalacticTradeFinder: адаптивный поиск без hard maxHops

## 1. Что хотим получить
Поиск межсистемной сделки должен останавливаться не по фиксированному числу хопов, а по экономическому смыслу.

Ключевой принцип:
- считаем **прибыль сделки**, а не только дельту цен;
- учитываем цену времени в ходах;
- дальний путь должен выигрывать у ближнего только если реально приносит больше пользы.

---

## 2. Что фиксируем как правила

### Делаем
1. Базовая метрика сделки:
   - `profit = (sellPrice - buyPrice) * amount`
2. Время маршрута:
   - `turns = EstimateTravelTurns(...)`
3. Цена времени:
   - `opportunityCost = baseline * turns`
4. Итог:
   - `netValue = profit - opportunityCost`
   - `score = netValue / turns` (или `netValue` для tie-break)
5. Поиск по кольцам BFS (`1, 2, 3, ...`) с ранней остановкой через upper bound.
6. Реплан — **один раз за сделку** (не каждый тик).

### Не делаем
1. Нет hard-лимита `maxHops = N` как бизнес-правила.
2. Нет сложной истории по кораблям (EMA/риск/волатильность) на этом этапе.
3. Нет отдельного "минимального порога доходности" с магическим числом.

---

## 3. Почему важно считать именно profit, а не дельту цен
Дельта цен сама по себе вводит в заблуждение.

Пример:
- Сделка A: дельта 100, объем 5 -> profit 500
- Сделка B: дельта 40, объем 200 -> profit 8000

Если сортировать по дельте, A выглядит лучше, но на деле хуже.
Поэтому первичный сигнал всегда:
- `profit = margin * amount`

Где:
- `margin = sellPrice - buyPrice`
- `amount = min(sellAmount, buyAmount, shipFreeCargo)`

---

## 4. Baseline: простой и дешевый вариант (без истории)
Baseline нужен, чтобы выразить "недозаработок за время полета".

### Источник baseline
Берем только из текущего прохода поиска (без новых подсистем):

В процессе скана считаем:
- `bestYield` — лучший `profit/turns`
- `avgPositiveYield` — средний `profit/turns` по прибыльным кандидатам
- `positiveCount`

Формула:
- если `positiveCount > 0`:
  - `baseline = lerp(avgPositiveYield, bestYield, 0.5)`
- иначе:
  - `baseline = avgYield` (fallback, который уже есть в системе)

Это дешево по CPU и без лишних аллокаций.

---

## 5. Как останавливать поиск без maxHops

### Идея
На каждой глубине `h` считаем верхнюю теоретическую границу, которую еще можно получить.
Если она уже хуже текущего лучшего результата — поиск дальше бессмыслен.

### Верхняя граница
Используем текущую экономическую константу:
- `EconomyConstants.MaxPriceDelta = 0.2`

Для товара:
- `maxUnitProfit ~= 2 * BasePrice * MaxPriceDelta`
- `maxProfit ~= maxUnitProfit * MaxTradableAmount`

Минимальные ходы на глубине:
- `minTurns(h) = h * JumpDurationTurns + 2 * ApproachTurns`

Граница:
- `upperBoundScore(h) = max(maxProfit(item) / minTurns(h))` по релевантным товарам

Условие остановки:
- если `upperBoundScore(h) <= bestScoreFound`, дальше не расширяем.

---

## 6. Узловой алгоритм (пошагово)
1. Стартуем из системы корабля.
2. Идем BFS-кольцами по хопам.
3. Для систем в текущем кольце собираем валидные пары sell/buy.
4. Для каждой пары считаем:
   - `amount`
   - `profit`
   - `turns`
   - `yield = profit/turns`
5. Обновляем агрегаты для baseline (`bestYield`, `avgPositiveYield`, `positiveCount`).
6. Считаем `baseline`.
7. Пересчитываем `score = (profit - baseline*turns)/turns`.
8. Обновляем лучший кандидат.
9. Считаем `upperBoundScore` для следующего кольца.
10. Если верхняя граница не бьет текущий best — выходим.

Результат:
- возвращаем один лучший кандидат (без списка и сортировки большого массива).

---

## 7. Что это даст в поведении
1. Дешевые товары отрежутся на малой глубине автоматически.
2. Дорогие товары могут идти глубже, но только пока это оправдано по `netValue`.
3. Больший трюм естественно дает преимущество на дальних рейсах.
4. Без hard-лимитов и без переусложнения экономики.

---

## 8. Минимальный план внедрения в код
1. В `GalacticTradeFinder` перевести поиск на BFS-кольца.
2. Встроить агрегаты для baseline в текущий проход.
3. Перейти на `profit`-first расчет с `opportunityCost`.
4. Добавить upper-bound остановку.
5. Оставить в `TradeGalaxyPlanner` реплан один раз за сделку.
