# Каркас ИИ

Этот документ описывает целевую организацию ИИ без привязки к текущим `TopShipOrder`, `ShipTaskStack`, `ShipActionPlanner` и другим существующим классам.

## Основная модель

```text
Базовое назначение
        ↓
Текущий приказ
        ↓
Корневое поведение приказа
        ↓
Составное поведение
        ↓
Исполняемая задача
        ↓
Local / Global Simulation Pipeline
        ↓
Результат задачи и события мира
        └──────── обратно в активное поведение
```

Между корневым поведением и исполняемой задачей может быть любое необходимое количество составных поведений. Искусственно фиксированная иерархия уровней не вводится.

## Базовое назначение и приказ

При создании агента задаются отдельно:

```text
Тип:
  технические возможности сущности

Владелец:
  кому сущность принадлежит

Базовое назначение:
  к какой постоянной обязанности агент возвращается

Текущий приказ:
  что агент должен выполнять сейчас
```

Тип и владелец не должны неявно определять назначение. Один военный корабль владельца-станции может охранять станцию, сопровождать транспорт, патрулировать сектор или находиться в резерве. Создатель агента передаёт базовое назначение явно.

```text
Свободный торговец:
  владелец: отсутствует
  базовое назначение: торговать в регионе

Охранник станции:
  владелец: станция A
  базовое назначение: охранять станцию A
```

Временный приказ может вытеснить базовое назначение. После завершения временного приказа агент повторно оценивает обстановку и возвращается к базовому назначению, если оно остаётся допустимым.

## Составные поведения

Составное поведение содержит логику принятия решений. Оно может:

- читать доступные агенту сведения о мире;
- хранить собственное рабочее состояние;
- выбирать дочернее поведение;
- выдавать исполняемую задачу;
- обрабатывать результат задачи;
- реагировать на значимые события;
- продолжать работу, перестраиваться, временно прерываться или завершаться.

Пример торговли:

```text
Приказ: торговать в радиусе 25 световых лет
└─ Поведение торговли
   └─ Выполнить выбранную сделку
      ├─ Лететь к продавцу
      ├─ Стыковаться
      ├─ Купить товар
      ├─ Лететь к покупателю
      ├─ Стыковаться
      └─ Продать товар
```

Пример исследования:

```text
Приказ: исследовать область
└─ Поведение исследования
   ├─ Выбрать неизвестную точку
   ├─ Лететь к точке
   ├─ Сканировать
   └─ Выбрать продолжение
```

`Торговать`, `исследовать область` и `атаковать цель` являются составными поведениями, если внутри них ещё требуется выбирать дальнейшие шаги.

## Исполняемая задача

Исполняемая задача — граница между ИИ и `Simulation`.

```text
ИИ:
  формирует запрос и параметры выполнения

Simulation:
  проверяет запрос
  выполняет его с нужной детализацией
  изменяет мир
  возвращает результат
```

Критерий исполняемой задачи:

> `Simulation` умеет принять её, выполнять до завершения и вернуть однозначный результат без дополнительных решений верхнего поведения.

Примеры-кандидаты:

```text
Лететь к объекту
Стыковаться
Купить товар
Продать товар
Сканировать объект
```

Исполняемая задача может длиться много тиков или рассчитываться укрупнённо за ход. Поэтому она не называется атомарной операцией.

`Атаковать цель` пока не признаётся исполняемой задачей автоматически: если внутри требуется выбирать дистанцию, манёвр, оружие и момент отхода, это составное реактивное поведение.

## План

`План` не является обязательным узлом общего каркаса.

Поведение может использовать:

- заранее созданный список задач;
- короткий план на ближайшие шаги;
- выбор следующей задачи по результату предыдущей;
- реактивное поведение без длинного плана.

Пример: торговля может хранить явный план сделки, а бой — регулярно выбирать следующее действие из текущей обстановки.

Общий тип плана выделяется только после подтверждения, что одинаковая модель плана нужна нескольким разным поведениям.

## Состояние исполнения задачи

Описание задачи, её состояние исполнения и результат нельзя объединять в один изменяемый объект.

```text
Описание задачи:
  создаётся ИИ
  после выдачи не изменяется
  содержит тип задачи и её смысловые параметры

Состояние исполнения:
  создаётся и изменяется Simulation
  содержит текущую фазу и служебный прогресс выполнения

Результат:
  создаётся Simulation при завершении
  после создания не изменяется
  возвращается активному поведению
```

Общий жизненный цикл должен быть небольшим. Активные состояния:

```text
Ожидает запуска
Выполняется
Отменяется
```

Конечные исходы:

```text
Успешно
Ошибка
Отменена
Отклонена
```

`Отклонена` означает, что `Simulation` не приняла запрос: например, исполнитель не существует или задача неприменима к его возможностям. `Ошибка` означает, что запрос был принят и начал исполняться, но его контракт выполнить не удалось.

Фаза вроде «ожидает разрешения на стыковку» не должна автоматически становиться общим состоянием жизненного цикла. Это специфичное состояние исполнения задачи стыковки, пока общая задача остаётся в состоянии `Выполняется`.

Общее состояние `Приостановлена` пока не вводится. Для первого каркаса прерывание низкоуровневой задачи оформляется как отмена; после этого поведение при необходимости создаёт новую задачу.

Смысловой прогресс, необходимый после переключения между Local и Global Simulation, должен сохраняться. Чисто физический прогресс, который однозначно читается из мира — например, текущая позиция корабля, — отдельно дублировать не следует.

## Результат задачи

Результат относится к конкретной исполняемой задаче и должен содержать:

```text
Идентификатор задачи
Конечный исход:
  успешно
  ошибка
  отменена
  отклонена

Типизированную причину, если она нужна:
  товар закончился
  цель исчезла
  путь недоступен
  приказ отменён

Типизированные данные конкретного результата:
  фактически купленное количество
  достигнутая позиция
  обнаруженные объекты
```

Универсального исхода «выполнено частично» нет. Частичность без контекста неоднозначна: это может быть как допустимый успех, так и ошибка.

Пример: контракт `Купить до 100 единиц` разрешает купить меньше при недостатке товара. Покупка 60 единиц завершается исходом `Успешно`, а число 60 хранится в данных результата. Если контракт требует купить ровно 100 единиц, тот же фактический объём завершается исходом `Ошибка` с причиной недостатка товара.

После результата исполнитель не очищает план, стек поведения и не выбирает восстановление. Он только завершает свою задачу. Активное поведение по результату и актуальному состоянию мира решает: продолжить, повторить, перестроиться или закончить приказ.

## Состояние и события

Состояние мира, результат задачи и событие не взаимозаменяемы.

```text
Состояние:
  что сейчас истинно в мире

Результат:
  чем закончилось выполнение конкретной задачи

Событие:
  что существенное произошло
```

Состояние мира является источником истины. Событие служит сигналом для повторной оценки и не заменяет чтение актуального состояния.

Пример попадания:

```text
Simulation:
  рассчитывает попадание
  изменяет здоровье и состояние модулей
  создаёт событие критического повреждения

ИИ:
  получает событие
  читает актуальное состояние корабля
  решает продолжать, атаковать или отступать
```

Высокоуровневый ИИ не должен получать каждое низкоуровневое событие вроде попадания отдельного снаряда, если достаточно агрегированного события `Атакован` или `Получено критическое повреждение`.

## Доставка событий

Основной вариант для проекта:

```text
Стадии Simulation создают типизированные события текущего шага
  → стадия Events завершает и распределяет буфер
  → относящиеся к агенту события попадают в его входящие сообщения
  → стадия AI читает их в следующей контрольной точке
  → активное поведение перепроверяет состояние мира и реагирует
```

Прямые C#-подписки каждого агента на общую шину не выбираются базовым решением из-за:

- сложного порядка вызовов;
- риска забытых подписок;
- большого количества агентов;
- отдельного потока глобальной симуляции;
- требований к детерминизму и сохранению состояния.

Окончательные форматы буферов и входящих сообщений проектируются отдельно.

## Роль пайплайнов

Существующие локальный и глобальный пайплайны сохраняются как оркестраторы расчёта.

```text
Input
  → Perception / подготовка сведений
  → AI
  → Movement
  → Interaction
  → Combat
  → Events
  → Snapshot
```

Пайплайн задаёт порядок стадий, но не является иерархией ИИ.

Стадия `AI` должна:

- передать агентам результаты и события прошлой контрольной точки;
- продвинуть активные поведения;
- получить новые исполняемые задачи для последующих стадий.

Стадии `Movement`, `Interaction` и `Combat` исполняют задачи и меняют мир. Стадия `Events` завершает сбор результатов и событий, предназначенных для следующей контрольной точки.

Поток одной задачи через пайплайн:

```text
AI создаёт неизменяемое описание задачи
  → подходящая стадия Simulation принимает или отклоняет задачу
  → Simulation изменяет только состояние её исполнения
  → Simulation создаёт неизменяемый конечный результат
  → Events доставляет результат агенту
  → активное поведение выбирает продолжение
```

Одна смысловая задача поддерживает два способа исполнения:

```text
Local:
  подробное выполнение по тикам активной системы

Global:
  укрупнённое выполнение за внутриигровой ход
```

ИИ не делится на независимые локальный и глобальный варианты только из-за разной детализации `Simulation`.

## Состояние текущей реализации

В существующем коде пайплайны уже задают полезный порядок стадий, но событийный цикл ещё не завершён:

- `LocalEventsStage` и `GlobalEventsStage` являются заглушками;
- локальный `SimulationEventBus` очищается в начале каждого тика;
- `LocalSimulationContext` не содержит ссылку на буфер событий;
- глобальный worker создаёт отдельный буфер на ход, который после выполнения не передаётся дальше;
- стадии `AI` напрямую вызывают конкретные планировщики торговли, докинга и патруля;
- явного общего жизненного цикла и объекта результата задачи нет;
- вершина `ShipTaskStack` неявно считается текущей задачей, а `Pop` используется и для успеха, и для пропуска задачи;
- ожидание, невозможность выполнения и ошибка местами различаются только управляющим потоком исполнителя;
- `CurrentAction` и `LastActionFailReason` образуют параллельное состояние рядом со стеком задач;
- исполнители торговли при некоторых ошибках очищают весь стек задач и тем самым сами выбирают способ восстановления.

Эти наблюдения не являются указанием немедленно менять код. Они учитываются при будущем плане миграции.

## Пока не проектируется

```text
Точная структура классов и папок
Общий формат плана
Физический формат хранения разнородных задач и их состояний
Фракционный и флотский ИИ
Внешний язык скриптов
Механизм распределения задач между агентами
```

Сначала определяются контракты составного поведения, исполняемой задачи, результата и входящего события.
