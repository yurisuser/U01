# План: межзвёздная торговля

Цель: обеспечить торговые рейсы между системами (по гиперлинкам) без костылей, с корректной экономикой и оффлайн-симуляцией.

## Архитектурные принципы
- Разделяем уровни: стратегия (выбор маршрута/контракта), выполнение (движение/прыжки/док), экономика (резервы и сделки), оффлайн-симуляция (в неактивных системах).
- Единый источник правды по рынкам/станциям (данные в `StarSys`, обновления через экономический сервис).
- Оффлайн-исполнение приказов кораблей в глобальном пайплайне, без привязки к активной системе.
- Jump/Continuum — транспортный слой, не знает о торговле; торговля подписывается на события прибытия/докинга.

## Шаги реализации
1. **Данные и приказы**
   - Добавить `TopShipOrder.TradeGalaxy` с параметрами: продавец (systemId/stationUid), покупатель (systemId/stationUid), товар, объём.
   - Расширить `ShipTask` шаблоном маршрута: `MoveToPoint(zone) -> JumpToSystem -> MoveToPoint(station) -> Dock -> TradeBuy/Sell`, поддержка многопрыжкового пути (цепочка систем).

2. **Маршрутизация по гиперлинкам**
   - Сервис поиска пути по `HyperlinkEdge` (A* или BFS, вес — число прыжков; позже можно учесть опасность/пошлины).
   - Генератор задачи: превращает контракт в последовательность `JumpToSystem` шагов с зонами отправления/назначения для каждой пары.

3. **Оффлайн-симуляция кораблей**
   - Глобальный пайплайн: тик оффлайн-систем — обработка ShipTasks (MoveToPoint в зону, Jump, прибытие) без локальной физики, дискретно по дням.
   - ContinuumService остаётся для сегмента прыжка; оффлайн-движение по системе — упрощённо: “долетел за ход до зоны/станции” или через время в ходах (константа скорости).

## Поиск кандидатов (детализация без жёстких порогов)
- Источник данных: станции + прайс-листы из `StarSys.Stations`. Индекс по товару: top-K продавцов/покупателей (по цене/наличию) на основе текущего состояния.
- Поиск пути: BFS/A* по `HyperlinkEdge` с кэшем кратчайших хопов (on-demand). Инкрементальный радиус: начинаем с 1–2 хопов, расширяем, пока не набран топ-K кандидатов или улучшение score не происходит.
- Кандидат = пара (продавец, покупатель, товар, объём, hopsToSeller, hopsSellerToBuyer), формируем `GalacticTradeCandidate`.
- Оценка: `yield = profit/turns`, где `turns = (hopsToSeller + hopsSellerToBuyer)*JumpDurationTurns + ApproachTurns*2`. Score = `yield / avgYield` (avgYield — EMA по выполненным рейсам или среднее по кандидатам шага).
- Отсев:
  - Верхняя граница: если теоретический maxYield для оставшихся (лучшая маржа / минимальные хопы) ≤ текущего лучшего score — ранний выход.
  - Минимальный relative score: discard, если `yield <= 0` или `score` заметно ниже среднего (например, `score < 0.5 * median` — динамический, не константа).
- Output: отсортированный список кандидатов (score desc), топ-K (K небольшое, например 5–10 — можно вынести в настройку).

## Компоненты для реализации поиска
- `GalacticRouteFinder`: API `TryGetHops(int fromSystem, int toSystem, out int hops)` с кэшем (словарь ключ=(a,b)). На вход — `HyperlinkEdge[]`.
- `GalacticTradeFinder`: принимает galaxy, станции, текущее положение/флот. Генерирует кандидатов (продавцы/покупатели в пределах растущего радиуса), вызывает `GalacticTradeScoringService`, возвращает топ-K.
- Интеграция с планнером: планнер запрашивает кандидатов, получает лучший, строит стек задач (`MoveTo zone -> Jump... -> Dock/Buy -> Dock/Sell`).
