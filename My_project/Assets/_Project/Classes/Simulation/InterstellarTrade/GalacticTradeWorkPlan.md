# GalacticTradeWorkPlan.md

Назначение: рабочий план реализации межсистемной торговли (`TradeGalaxy`) без костылей, с корректной архитектурой для локальной и глобальной симуляции.

---

## 0) Границы и правила

- [ ] Не смешивать слои: поиск сделки, поиск пути, сборка задач, исполнение рейса.
  - Комментарий: это критично, чтобы не получить «умный god-service», который потом нельзя расширять.
- [ ] `Continuum` остаётся транспортным слоем, не хранит торговую логику.
  - Комментарий: прыжок не должен знать про buy/sell, только про перемещение между системами.
- [ ] Модель времени в скоринге должна совпадать с моделью времени исполнения.
  - Комментарий: иначе выбор «лучшей» сделки будет системно ошибочным.
- [ ] `TaskStack` торговли имеет одного писателя (`single-writer`): только `TradeActionPlanner/TaskComposer`.
  - Комментарий: стадии исполнения не переписывают торговый стек, а только исполняют верхнюю задачу.

---

## 1) Контракты данных (спека до кода)

- [ ] Зафиксировать структуры:
  - `GalacticPath` (последовательность систем маршрута),
  - `GalacticTradeCandidate` (seller/buyer/item/amount/цены),
  - `TopShipOrderParams` как единственный контракт намерения рейса.
  - Комментарий: пока не зафиксированы контракты, код писать нельзя.
- [ ] Зафиксировать инварианты:
  - `path.Systems[0] == fromSystem`, `path.Systems[^1] == toSystem`,
  - `hops` вычисляется как `path.Systems.Length - 1` (не хранится отдельным полем),
  - валидность пути — результат проверки инвариантов/фабрики, а не хранимый флаг,
  - состояние исполнения рейса выводится из `TaskStack` и `Cargo`, без отдельной сущности рейса.
  - Комментарий: это база для детерминизма и отладки.

---

## 2) Маршрутизация (не только hops)

- [ ] Ввести сервис полного маршрута:
  - API: `TryBuildPath(fromSystemIndex, toSystemIndex, edges, out GalacticPath path)`.
  - Комментарий: `hops` использовать только как производную метрику из маршрута.
- [ ] Кэш маршрутов + правила инвалидации при изменении графа гиперлинков.
  - Комментарий: без кэша поиск быстро станет дорогим на больших галактиках.

---

## 3) Поиск торговых кандидатов

- [ ] Ограничить `GalacticTradeFinder` только поиском экономических пар.
  - Комментарий: finder не должен собирать `ShipTask`.
- [ ] Добавить постепенное расширение радиуса поиска по хопам.
  - Комментарий: это даёт хороший баланс качества/стоимости поиска.
- [ ] Подготовить индекс рынков по товару (`itemId -> sellers/buyers`).
  - Комментарий: без индекса будет O(N^2) по станциям.

---

## 4) Сборка плана задач рейса

- [ ] Ввести `GalacticTradeTaskComposer` (отдельный слой).
  - Комментарий: composer превращает `candidate + path` в стек `ShipTask`.
- [ ] Поддержать многопрыжковый маршрут:
  - `MoveToZone -> Jump` для каждого ребра пути,
  - затем `MoveToStation -> TradeBuy`,
  - затем путь до buyer и `TradeSell`.
  - Комментарий: текущая модель с прямой парой систем недостаточна.
- [ ] Явно определить точку, где выставляется скорость/ориентация при межсистемном переходе.
  - Комментарий: поведение должно быть одинаково в локале и глобале.
- [ ] Жёстко зафиксировать канон стека `TradeGalaxy` (шаблон задач и их порядок).
  - Комментарий: по канону должно быть однозначно понятно, где корабль в цикле (до покупки/после покупки/доставка).

---

## 5) Исполнение и fail-handling (lean-вариант)

- [ ] Не вводить отдельные `GalacticTradeRun` и `GalacticTradeFailReason` на этом этапе.
  - Комментарий: используем `TopOrder + TaskStack + Cargo`, без лишних сущностей.
- [ ] Зафиксировать таблицу реакций `причина -> действие` на уровне планнера:
  - fail до покупки (целевого товара в трюме нет): `TaskStack=Default`, затем сборка нового рейса из `TopOrder`.
  - fail после покупки (товар в трюме есть): приоритетная разгрузка груза (поиск buyer), затем возврат к обычному рейсу.
  - buyer недоступен: fallback (поиск альтернативного buyer; если не найден — парковка/сброс приказа по политике).
  - Комментарий: запретить silent-fail и бесконечные зависания.
- [ ] Перестройка пути только по событиям, а не по каждому тіку:
  - пустой `TaskStack`,
  - явный fail,
  - недоступность следующего сегмента маршрута.
  - Комментарий: это даёт стабильность и не перегружает поиск.

### Заметка: приоритет разгрузки текущего груза

- [ ] Если в трюме уже есть товар, перед новым `TradeGalaxy` сначала выполняем его продажу.
  - Комментарий: не стартуем новый цикл покупки, пока не освобождён трюм от старого рейса.
- [ ] Если buy-ордера на этот товар нет, выполняем `forced-sell`.
  - Комментарий: товар списывается из трюма и не попадает на склад станции.
- [ ] Цена `forced-sell` берётся как средняя/базовая из каталога (`price`).
  - Комментарий: деньги начисляются владельцу корабля по фиксированной каталожной цене.
- [ ] Правило исчезновения товара применяется только к `forced-sell`.
  - Комментарий: обычная продажа по buy-ордеру работает штатно через `ExchangeService`.

---

## 6) Скоринг и ETA

- [ ] Привести `GalacticTradeScoringService` к реальной модели длительности:
  - прыжки (`JumpDurationTurns`),
  - подлёты по дистанции/скорости (не фиктивная константа),
  - сервисные действия (dock/trade), если они занимают ход.
  - Комментарий: единая формула должна использоваться и в выборе, и в фактическом исполнении.
- [ ] Относительный score оставить как `yield/avgYield`, но считать `yield` на реальном ETA.
  - Комментарий: это даст корректный приоритет ближних/выгодных рейсов.

---

## 7) Логи и наблюдаемость (временный режим)

- [ ] Логировать один торговый цикл по `ShipUid` в структурном формате.
  - Комментарий: лог нужен для верификации исполнения канонического стека и причин сбоев.
- [ ] Логи писать вне `Assets`.
  - Комментарий: иначе Unity SourceAssetDB будет давать import-ошибки.
- [ ] После стабилизации оставить флаг `Enabled=false` по умолчанию.
  - Комментарий: снижает шум и исключает лишние I/O в рантайме.

---

## 8) Приёмка (Definition of Done)

- [ ] Один тестовый корабль стабильно выполняет полный `TradeGalaxy` цикл по пути с 2+ прыжками.
- [ ] В случае рыночного/маршрутного сбоя корабль не зависает: применяется политика из таблицы `причина -> действие`.
- [ ] На одинаковом сценарии итоговое состояние после N ходов консистентно между локалом и глобалом.
- [ ] Нет скрытых телепортов, кроме явно допустимых (прыжок через Continuum).

---

## Порядок выполнения (рекомендуемый)

1. Контракты данных и правила исполнения (`Раздел 1`, `Раздел 5`).
2. Полный путь и кэш (`Раздел 2`).
3. Finder + индекс рынков (`Раздел 3`).
4. TaskComposer (`Раздел 4`).
5. Скоринг/ETA (`Раздел 6`).
6. Логи и приёмка (`Раздел 7`, `Раздел 8`).

Комментарий: этот порядок минимизирует риск переписывания уже сделанного кода.
