## Флаги поведения (переключатели, которые могут прицепляться к любому приказу)
- `WeaponActive` — включить/выключить вооружение (чтобы «борьба» была флагом, а не отдельной задачей).
- `AvoidCombat` — стараться избегать боя (использовать уклонение, не входить в радиусы врагов).
- на потом `IgnoreMining` — запретить автоматические добывающие действия.
- на потом `HoldFormation` — сохранять строй (ограничивает движение и дистанцию).
- на потом `AutoRepair` — автоматически искать ремонт, если хп ниже порога.

## ShipTask: общий формат
```csharp
struct ShipTask
{
    ShipTaskType Type;            // Navigation, Combat, Trade, Special...
    ShipTaskParams Params;        // Обёртка с параметрами конкретной команды
    ShipBehaviorFlags Flags;      // Bitmask флагов поведения (WeaponActive/AvoidCombat/…)
}
```
- `ShipTaskType` — enum с конкретными командами (MoveToPoint, FollowEntity, AttackTarget, PatrolRoute…).
- `ShipTaskParams` — обёртка, внутри которой лежат отдельные структуры по подтипам (MoveToPointParams, AttackParams и т.д.)
- `ShipBehaviorFlags` — `Flags enum` (битовые флаги), чтобы быстро переключать вторичные режимы.
- Команда может содержать стек/список «подзадач», если это сложный сценарий (например, MoveToSystem = последовательность `MoveToPoint -> Jump -> MoveToPoint`), но внешне всё равно выглядит одним `ShipTask`.

### ShipTaskParams (типизированный union)
`ShipTaskParams` хранит несколько структур-параметров, но активен только один вариант. Дополнительно вводим enum `ShipTaskParamsType`, чтобы помечать, какие данные валидны.
```csharp
struct ShipTaskParams
{
    ShipTaskType Type; // MoveToPoint, AttackTarget, TradeSell, ...

    MoveToPointParams MoveToPoint;
    FollowEntityParams FollowEntity;
    PatrolRouteParams Patrol;
    AttackTargetParams AttackTarget;
    AttackEnemiesParams AttackEnemies;
    DefendTargetParams Defend;
    TradeSellParams TradeSell;
    TradeBuyParams TradeBuy;
    SpecialScanParams SpecialScan;
    // … добавляем новые по мере роста списка задач
}
```
- Заполняется только та структура, которая соответствует `ShipTaskType`.
- Примеры:
    - `MoveToPointParams { Vector2 Target; float Tolerance; }`
    - `FollowEntityParams { UID TargetUid; float DesiredDistance; }`
    - `AttackTargetParams { UID TargetUid; AttackPriority Priority; }`
    - `TradeSellParams { UID StationUid; TradeItem[] Items; }`
- Такой подход оставляет структуру типобезопасной и не раздувает данные лишними полями.
- При создании команды выставляем `Type` и заполняем только соответствующий блок (например, `Type = ShipTaskType.AttackTarget`, `AttackTarget = new AttackTargetParams { ... }`). Остальные структуры остаются default.

## «Лететь в систему» — пример разбивки
1. `MoveToPoint` — долететь до ближайшего прыжкового узла (ворота/портал).
2. `JumpToSystem` — выполнить переход (может быть отдельной командой с проверкой топлива/заряда).
3. `MoveToPoint` — по прибытии в новой системе летим к назначенной координате (например, к станции).
4. Дополнительно можно вставить `Wait/Sync` (ожидание окна прыжка) или `CheckClearance` (получение разрешения на док).

Эта последовательность может быть автоматически развёрнута внутри обработчика команды `MoveToSystem`: как только задача стартует, AIStage пушит в очередь подзадачи для MovementStage. Благодаря формату `ShipTask` тулчейн не меняется: мы всё ещё работаем через enum+параметры, просто задача композитная.

## PrimaryTask, TaskState, ShipTaskStack
- `PrimaryTask` — длительная роль корабля (патруль, автоторговля, добыча), которая повторяется бесконечно, пока игрок/скрипт не сменит назначение.
- `TaskStack` (TaskState) — стек конечных/временных задач: межсистемные перелёты, боевые реакции, ремонт. Они добавляются поверх и автоматически снимаются по завершении.
- `ShipTaskStack` — единое поле в структуре корабля, которое содержит `PrimaryTask`, `TaskStack` и вспомогательные таймеры/ссылки. Благодаря этому весь набор задач путешествует вместе с кораблём (перелёт в другую систему/сейв), и AI всегда знает, что нужно продолжить после временной задачи.

## Источники команд
- Команды кораблю выдаёт его владелец:
  - Если корабль принадлежит игроку — приказы приходят от игрока/UI.
  - Если корабль NPC — командует ближайший иерарх (фракционный контроллер, скрипт сценария).
- Это правило исключает гонки: одновременных приказов от разных систем не бывает, всегда есть один ответственный источник.
